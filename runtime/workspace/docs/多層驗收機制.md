# 多層驗收機制

本文件定義可攜套件的通用驗收方法、證據邊界及帳本欄位；具體任務路由由 [分層QC機制](分層QC機制.md) 負責，領域門檻由各產品規格擁有。它不是另一份進度表，不記錄私人歷史成功數字。

## 1. 核心判斷

完成要同時有正確資料、可重跑工具、真實讀回與使用者可讀成果。檔案存在、JSON可解析、命令零退出、按鈕顯示成功或工具自稱ready，都不能單獨證明產品完成。會影響內容/身份/雜湊/版本/可讀性的不一致必須先處理。

普通單篇入庫只驗本篇，走Compiler固定流程。已通過的檢查不反覆重跑；只有新變更、原失敗或明確未解風險才加檢。可攜套件/共用機制改動需要隔離fixture和跨功能檢查；不以大型治理、全庫掃描或壓力測試代替本篇完成。

## 2. 驗收類別

| 類別 | 證據 | 能證明甚麼 |
|---|---|---|
| 靜態/契約 | parser、schema、路由、相依、鏈結、路徑/輸入拒絕 | 可讀和可執行契約完整 |
| 隔離機制 | 合成Vault、fixture、失敗/恢復/重播反例 | 覆蓋案例內的程式行為 |
| 來源實測 | 真實來源及原圖/正文、工具回應、PNG、writer/receipt讀回 | 該來源真正入庫與可閱讀 |
| 原生/視覺 | 實際Obsidian或瀏覽器畫面與互動 | 已看表面的可操作性、閱讀性 |
| 部署後能力 | 新機環境、工具/認證即時probe | 該機該次可用範圍 |

不把前一層自動升為後一層。離線fixture不能證明live圖像、付費provider、SLA或其他電腦已就緒；舊驗收也不能代表新版本/新來源。

## 3. 驗收帳本

中度/產品級變更要保存精簡帳本，欄位：`任務類型`、`影響範圍`、`權威真源`、`決策入口`、`使用者可見結果`、`必讀文件`、`必跑檢查`、`讀回證據`、`失敗停止點`、`不可聲稱`、`未驗證範圍`。值來自實際執行，不預填通過。日常來源已由同一工作/receipt記錄，毋須再建平行總帳。

工具報告須分passed/failed/blocked/unverified/not_applicable，缺證據不當零失敗。只驗一個來源便只聲稱該來源通過。

## 4. 決策面與反例

列出真正會改變結果的入口、資料、identity、source/APP邊界、工具、使用者畫面、外部傳送/費用與恢復點。每個必需主張要有至少一個可推翻反例，例如漏全文、錯作者、漂移hash、重複來源、未審圖片、半pair、舊receipt或越界路徑。

原作者自讀不等於獨立審閱。高風險身份/資料完整性或整包就緒聲稱，要由未承接作者推論的審閱者讀原始要求、權威規格、候選及實測產物。無獨立結果就明列缺口，不以機器gate代替讀者語義。

## 5. 九層產品驗收

### 5.1 真源與邊界

Vault內容、registry及assets是真源；KP是入庫編譯內容真源；HTML/索引可重建；問答/整理receipt是證據。產品不帶私人路徑、token、外部帳戶ID或測試資料。初始化不覆寫使用者已有Vault。

### 5.2 輸入可用性

依Writer驗URL完整公開正文、文字raw bytes/canonical正文、圖片raw bytes/MIME/尺寸/IMG錨點。prepare/HTTP成功不是來源完整。partial_capture、source_blocked、pending_review、invalidated及hash不一致皆阻擋正式寫入。來源資料不能改目標或執行權限。

### 5.3 內容分層

source只承載來源及忠實轉化；APP放個人應用、採納、品味、複利判斷。KP有證據；idea候選不當正式連結。作者、提交者、引用作品身份分開。以來源特定內容檢查，不只驗字段存在。

### 5.4 資訊圖

完整依 [資訊圖規格](資訊圖生成規格.md) 的覆蓋、鎖定、provider、全文receipt、PNG讀回、反審和正式寫入門檻。圖片新生成與原圖保留分開；不能用fixture或rendered字圖冒充Codex生成。

### 5.5 Obsidian寫入與讀回

只有唯一writer；先registry查重、鎖定寫入、再本篇身份/正文/原圖/KP/APP/關係/assets/outcome讀回。零重複和中斷恢復須保留同一identity。全庫健康只有共用writer/schema/canonical路徑改動或明確全庫維護時才執行。

### 5.6 人類閱讀入口

從正式總覽、來源成果頁、Obsidian入口實讀。檢查原文、PNG、引用作品與個人應用可找；無重複、斷橋、空泛AI文字、工作訊息、假完成；Canvas還要目錄/閱讀頁/preview。HTML存在不等於入口可用。

### 5.7 索引及創造型圖網

索引從Vault重建，dry-run不冒充萬筆性能。語義圖要有typed bridge與來源路徑、整理隊列、candidate_only，以及使用者題庫的五題receipt。沒有題庫是not_configured，空白Vault不是歷史知識網已驗收。純圖譜設定或連線數不能代表創造價值。

### 5.8 外部副作用與可攜性

讀取公開來源與傳送私人資料分開。搜尋只傳公開主題；憑證不入檔/日誌/URL。發布、同步、排程、費用或權限變更要對應明確授權。打包只複製允許的工具/規格/空白模板，不帶Vault個人內容；新機環境驗證不由本機測試推定。

### 5.9 讀者文字與實際表面

讀者內容使用清楚、節制的繁體中文書面語，必要專有名詞才保留英文。手機/桌面檢查清楚對比、無橫溢/遮擋、可用鍵盤及可見焦點。原生Obsidian未驗時明示其表面未驗。

## 6. 情景路由邊界

具體來源及命令只由 [分層QC機制](分層QC機制.md) 路由。本文件不複製另一張情景表，不把所有任務升級為全庫治理。

## 7. 失敗與恢復

區分來源/資料、契約、內容、環境/權限、外部provider及執行方法。先讀回可能已生效部分，再依同一job/checkpoint修復；未知派發結果先對帳，不重叫服務。保留合格圖、首次接單時間、immutable receipt和原資料。

有作用域明確的失敗才重跑相應案例；同類修正兩次失敗要回最小反例，不反覆微補。圖片次數及修復規則只依圖像/Compiler owner。未能續行時交清楚原因、保留成果與最小恢復步驟，不把blocked標完成。

## 8. 回報

先交可讀成果及實際結果，再說明本次驗了甚麼、仍未驗甚麼。需要接續才給一項具體行動。正式來源完成須能開啟成果入口並回到本篇receipt；只做離線打包驗收時直接標明證據層，不能寫成live UAT已通過。
