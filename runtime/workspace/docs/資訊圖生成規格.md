# 資訊圖生成規格 v3｜手繪知識卡片母版

> 目的：把 Second Brain 中已驗證的內容來源，轉成第三方讀者可快速理解、可追溯、可入庫的手繪知識卡片式 PNG 資訊圖。
>
> 內容來源包括公開 URL、文章、影片、書籍、報告、論文、圖片、使用者明確提供文字、使用者明確提供圖片及其他已入庫或待入庫材料。URL 只是其中一種輸入，不是本規格的中心。
>
> 本文件只規範資訊圖的內容設計、文字鎖定、視覺母版、生成驗收與入庫前門檻；不改現有內容入庫功能、Vault writer、outcome page、registry、Compiler Worker 或相容 pipeline 流程。

## 1. 單一權威與不變邊界

資訊圖是內容來源的助讀成果，不是工作紀錄、後台狀態、操作介面、摘要截圖、簡報模板或裝飾海報。讀者離開製作對話、專案工作區和原始輸入情境後，仍應能直接看懂主題、重點、限制、關係與追溯來源。

本文件是資訊圖內容、視覺方向與生成驗收的唯一規格。`docs/URL到輸出模板規格.md` 只保存正式 PNG 路徑、雜湊與 source note embed；`docs/Compiler Worker與Knowledge Package設計及驗收規格.md` 只描述 Knowledge Package、worker 與 writer 邊界；`tools/infographic_prompt_contract.py` 是本文件的唯一可執行 prompt 母版。不得在其他文件、工具或臨時提示中另立第二套資訊圖風格規則。

本規格的生成 provider/model、prompt/attempt 帳本及新生成簽名要求適用於本次新生成的資訊圖。使用者文字附現成 PNG 並明確要求保留時，依 `docs/URL到輸出模板規格.md` 第 12 節保存原 bytes 與原 footer，不偽造新生成證據、不改簽名、不重新生成；仍要通過本規格的來源、可見文字、風格、反審、PNG 品質及正式讀回。這項保留分支不適用於拿舊圖冒充本次新生成。

現有流程不變：來源擷取、轉寫、摘錄或審閱先產生 source slice 或 Knowledge Package；資訊圖先完成覆蓋表與逐頁鎖定稿；再由正式 prompt contract 派發 Codex imagegen / `gpt-image-2` 生成 PNG；完成圖片讀回、語義驗收、視覺安全檢查及雜湊綁定後，才交由既有 ingest / writer 寫入 Vault、registry、assets 與 outcome page。

不得用 HTML、SVG、CSS、browser screenshot、canvas、本地 renderer、fixture、placeholder、舊圖轉檔或後期疊字冒充正式資訊圖。正式成果必須是真 PNG，而且視覺上不得像乾淨 SVG 拼圖、企業 dashboard 或完美 UI card 組合。

任何資訊圖生成、修改、反審或正式入庫前，必須先讀入本規格全文，而不是只讀搜尋命中、局部段落、摘要、contract block 或舊記憶。正式反審證據必須包含由目前全文計算的 `spec_full_sha256` 與 `spec_chars` 讀回 receipt；writer 必須用本檔全文即時計算並比對，不吻合即拒絕正式入庫。這個 receipt 只證明規格全文已被流程讀入與版本綁定，不能取代逐項語義反審、Bauhaus 風格反審、footer 反審或 PNG 視覺 QC。

## 2. 長期判斷句

一張合格資訊圖，不是把原文變成漂亮框，而是把讀者原本要花時間整理的判斷、流程、差異或限制，變成一眼能跟住看的手繪知識卡片。

這句是所有資訊圖的最高讀者價值標準。若某張圖雖然來源正確、PNG 可讀、欄位齊全，但讀者仍要自己回原文重新拆解，該圖仍不合格。

合格資訊圖至少回答下列三個問題中的兩個：

1. 這份來源在說甚麼？
2. 哪些概念、限制、流程、比較或證據最影響理解？
3. 讀者看完後應如何判斷、使用、深讀、保存或避開誤用？

每張圖只承擔一個清楚任務。它可以是「理解一個概念」、「完成一個判斷」、「看清一組限制」、「比較兩種情境」、「追一條流程」或「辨認來源證據」。不得把幾個無關重點放進同一張圖，亦不得為湊頁數把正文硬切成幾頁。

30 秒快讀是核心驗收。讀者在手機縮圖或 outcome page 預覽中，應先看到主題與結構，再看到細節；若需要逐字讀完整張圖才明白主旨，設計失敗。

## 3. 四道生成閘門

### 四道生成閘門

1. 來源閘門：來源主體完整、可追溯、已完成審閱；`source_blocked`、`partial_capture`、未驗證外部聲稱或只有處理紀錄的內容，不得生成正式資訊圖。
2. 讀者閘門：每頁先寫清 `本頁讀者問題`、`本頁一句讀後收穫`、`本圖分工`、`跨頁承接`；無法回答讀者問題，不得生成。
3. 視覺理解閘門：圖面必須有可跟讀的層級或關係，核心文字不可因分區、圖示或版式而難讀、裁切或改變意思。Bauhaus 手繪方向是品質目標，不能單獨阻止入庫。
4. 入庫閘門：正式 PNG 必須綁定 provider/model、prompt hash、PNG SHA-256、圖片讀回、語義驗收、視覺 QC 及 Vault 寫入讀回；任一缺失不得入庫。

四道閘門不可互相代替。機器欄位齊全不能代替讀者閘門；好看的視覺不能代替來源閘門；自動 QC 通過不能代替獨立讀回對核心內容、可讀性及關係的核對。

## 4. 來源與覆蓋

來源形態不改變資訊圖標準。公開 URL 要有可讀正文；文章、報告與論文要有可追溯標題、作者或發布資料；影片要有可信轉寫、字幕、章節或逐段筆記；書籍要有可追溯書名、章節、頁碼或摘錄位置；圖片要有原圖 bytes、SHA-256、可見內容轉寫及必要外部核實；使用者提供文字要保留原始 bytes 身分與可讀文本。

所有圖中文字必須能追到來源內容或忠實編排需要。不得把下列內容畫入圖面：製作流程、欄位名稱、審核狀態、工具名、儲存位置、使用者個人指令、工作區狀態、重試原因、coverage ID、校對紀錄、後台 schema、未入庫判斷、模型提示語。

生成前必須建立重要知識覆蓋表。覆蓋表不是摘要目錄，而是「來源中值得轉成助讀圖的知識單元」。每項只分配到一頁；不得一項多頁重複，也不得為節省頁數刪除核心內容。

```markdown
### 重要知識覆蓋表

| 覆蓋 ID | 類型 | 重要知識 | 原文證據 | 原文語氣 | 指定頁 | 圖面表達 |
|---|---|---|---|---|---:|---|
| K01 | 主張 | ... | ... | 事實 | 1 | ... |
```

`類型` 只使用：主張、數字、限制、比較、方法、例子、行動。

`原文語氣` 只使用：事實、定義、建議、限制、比較、例子、行動、作者詮釋、工具定位。

`原文證據` 是既有欄位名，實際意思是「來源證據」。它必須能在 canonical source 內容區、轉寫、摘錄、圖片審閱或其他正式來源真源中讀回。`圖面表達` 是將來可能出現在圖內的讀者文字，必須忠於來源語氣；不得把建議寫成硬限制，亦不得把限制淡化成提醒。

本規格保留部分既有欄位名及圖型名中的「原文」，例如 `原文資訊功能`、`原文實體錨點`、`原文重點卡`。這些名稱為現有工具與測試的相容契約；在語義上全部代表「內容來源」，不表示只支援 URL 或文字文章。

## 5. 頁數與敘事

頁數由讀者理解障礙決定，不由固定模板、生成成本或三頁習慣決定。一般來源可為 1 至 5 頁；需要更多頁時，應按章節或理解任務分卷。單頁也可以合格，只要覆蓋表證明沒有犧牲重要知識。

頁數裁決的必守流程是：先衡量核心內容量，再界定值得抽出的資訊圖範圍，最後才決定圖片數。凡覆蓋表已標為高重要性的核心主張、核心功能、流程、限制、方法或行動，不得因為想維持單頁、固定頁數、生成成本或版面方便而略過資訊圖；若已選入資訊圖的核心量超過每頁 3 至 5 個主點的承載範圍，必須增加頁數或回到覆蓋表重新合併成更高層級的核心單元。工具 gate 只可執行這條核心覆蓋規則，不得另立較寬鬆的頁數判斷。

多頁資訊圖必須形成閱讀路徑。每頁都要填寫：

- `本圖分工`：這頁負責解決哪一個理解任務。
- `本頁讀者問題`：讀者看這頁前最可能不明白甚麼。
- `本頁一句讀後收穫`：讀完這頁應帶走的一句清楚結論。
- `跨頁承接`：上一頁如何引出這頁，這頁如何推進下一頁；單頁寫明「單頁完成」。

多頁資訊圖集的第 1 頁預設不是普通重點頁，而是冷讀者導讀頁。只要總頁數大於 1，第 1 頁必須先回答三件事，並把相應文字放入圖面可見白名單：

1. `collection_thesis`：全文一句話在講甚麼。
2. `collection_importance`：為何這件事值得讀者先理解。
3. `collection_roadmap_summary`：後面幾頁會按甚麼邏輯展開。

第 1 頁還必須保留 `collection_roadmap`，逐頁列出頁碼、page_id、頁面短名與頁面角色。`collection_thesis` 和 `collection_importance` 必須可追到來源覆蓋單元；`collection_roadmap_summary` 是讀者可見的內容脈絡句，必須用成品語言回答「後面幾頁如何展開」，例如「後續脈絡：協作限制會連到低差異性 → 共識壓力 → turf war → governance」。它不可寫成 AI 工作要求、閱讀指令或製作說明，例如「全文地圖：先看主題、重要性與閱讀路線」或「閱讀路線：先定位全文，再拆重點」。第 2 頁起才逐個拆解重點、實驗、限制或應用。

每頁正文正常只放 3 至 5 個主點。若來源本身需要清單、步驟或逐列比較，可放到 8 個主點，但必須在 `正文敘事充足性檢查` 說明為何讀者仍能快速跟讀。超過 8 個主點應拆頁或改成更高層級圖。

多頁禁止重複。頁碼、底部來源行、必要主題錨點可以重複；正文、數字、版本號、容量、日期、欄名或短句若重複，必須在 `重複文字 / 數字檢查` 說明不同語義角色。沒有新作用的重複就是資訊密度失敗。

頁碼固定在右上角，格式為 `當前頁 / 總頁數`，例如 `1 / 3`。頁碼只是追溯元素，不得放進標題、正文、卡片、圖示或底部來源行，也不得在右上角以外重複。

## 6. 內容用途與圖型

`內容用途 / 圖型 / 圖面結構` 是機器 gate，不是創意模板。先判斷讀者要解決甚麼理解問題，再選最貼切的圖型；不得只因來源是官方文件、新聞、訪談、API 文件、影片、書籍、論文、圖片或個人筆記便套固定版式。

下表是唯一可用對應。`圖面結構` 必須填入相應 `kind` 及必填欄位；所有 `_text` 欄位必須同時出現在圖內可見文字白名單。

| 內容用途 | 可用圖型 | `visual_structure.kind` | 必填結構 |
|---|---|---|---|
| 事實真源 | 原文重點卡 | `fact_cards` | `items[].heading_text`, `items[].body_text` |
| 事實真源 | 限制卡 | `constraint_cards` | `items[].rule_text`, `items[].condition_text` |
| 事實真源 | 引用位置圖 | `citation_map` | `items[].point_text`, `items[].location_text` |
| 工作流程 | 原文流程步驟圖 | `process_steps` | `steps[].step_text`，至少 2 項 |
| 工作流程 | 決策路徑圖 | `decision_path` | `decisions[].question_text`, `yes_text`, `no_text` |
| 學習材料 | 核心定義卡 | `concept_definition` | `definition_text`, `parts[].part_text`，parts 至少 2 項 |
| 學習材料 | 概念拆解圖 | `concept_parts` | `center_text`, `parts[].part_text`, `parts[].relation`，parts 至少 2 項 |
| 學習材料 | 結構層級圖 | `hierarchy_levels` | `levels[].level_text`, `levels[].detail_text`，至少 2 層 |
| 判斷材料 | 比較對立圖 | `comparison_rows` | `left_label`, `right_label`, `rows[].basis`, `left_text`, `right_text`，rows 至少 2 項 |
| 判斷材料 | 風險盲點圖 | `risk_map` | `items[].risk_text`, `items[].consequence_text` |
| 判斷材料 | 證據階梯圖 | `evidence_ladder` | `levels[].evidence_text`, `levels[].meaning_text`，至少 2 層 |
| 品味材料 | 原文品味線索圖 | `taste_signals` | `signals[].signal_text`, `signals[].meaning_text`，至少 2 項 |
| 品味材料 | 作品脈絡圖 | `work_context` | `nodes[].id`, `nodes[].node_text`, `links[].from`, `to`, `relation` |
| 品味材料 | 選擇特徵圖 | `choice_features` | `rows[].feature_text`, `choice_text`, `meaning_text`，至少 2 項 |
| 行動材料 | 原文行動步驟圖 | `action_steps` | `steps[].action_text`, `steps[].check_text`，至少 2 項 |
| 行動材料 | 驗證問題卡 | `verification_questions` | `questions[].question_text`, `questions[].check_text` |
| 噪音暫存 | 最小摘要卡 | `minimal_summary` | `items[].text`；不得進入正式生圖 |

選型裁決：

- 來源提供可查事實或限制，選事實真源。
- 來源說明先後、操作、發布、修復或決策路徑，選工作流程。
- 來源主要解釋新概念、理論、書中觀念、影片教學或結構，選學習材料。
- 來源幫讀者比較方案、辨認風險、判斷證據或理解爭議，選判斷材料。
- 來源呈現作品、地方、品牌、人物、工具或體驗線索，選品味材料。
- 來源要求讀者做下一步或自我檢查，選行動材料。
- 來源價值不足以生成助讀圖，選噪音暫存並停止正式生圖。

## 7. 圖文鎖定稿

生成前，每頁必須有完整文字鎖定稿。鎖定稿是正式 prompt、圖片讀回及入庫驗收的共同真源；生圖後不得為遷就成圖而改鎖定文字。

鎖稿前先寫可獨立理解的完整圖面文字，再壓縮重複，不得刪掉主詞、動作對象、條件、結果或首次出現術語的必要解釋。先按真實概念關係選圖型，不得把第一句自動當中心、末句自動當收穫，或平均切割知識點湊頁。後續頁仍須自足；跨頁承接不能代替本頁背景。

每頁由未參與製稿的讀者先只讀該頁標題、讀者問題、可見文字和圖面結構，不看原文、作者收穫或其他頁；用自己的話回答問題，解釋相鄰區塊為何相連，指出不懂的術語、缺少的情境及誤導關係。之後另做來源忠實核對。`reader_review` 保存讀者身分、方法 `isolated_page_readback`、回答、關係解釋、三類缺口清單與裁決，並以 `page_sha256` 綁定實際頁面。文字或結構修改後須重新讀回；空白欄位、制式通過句、來源引用及機器關鍵字檢查不能代替理解證據。程式只能核對證據與版本，不聲稱自動判懂。


圖面標題必須表達知識主題。若來源標題以「本週精選」加冒號起首，該欄目字樣不屬於知識主題，須從圖面標題移除；來源筆記仍保留完整提交標題與來源身分。

圖中文字必須自足、短而厚實。`自足` 是指讀者只看圖面文字，不看 source note、覆蓋表或原文，也能知道每句在說哪個對象、哪個判斷、哪個限制或哪個後果。`短` 是指刪走鋪墊、重複和後台詞，不把長段落塞入圖。`厚實` 是指每句都帶有實際資訊量，最好同時含有「對象 + 判斷 / 動作 + 後果 / 用途」中的至少兩項；孤立名詞、欄名、半句、口號、純標籤、只有版本號或只有角色名都不合格。

圖內正文優先寫成可單獨讀懂的短句，例如「終端難讀才值得發布」、「要後端就改做正式 app」、「editor 可發布新版本」、「缺 connector 要有 fallback」。不得使用「私有 URL；版本」、「viewer / editor；public link」這類只有標籤沒有判斷的薄句，除非同一視覺區內已有清楚句子補足其語義。

收束句、使用提醒與圖中大字提示不得使用生成式泛句。`具實用性`、`具啟發性`、`很重要`、`真正有用`、`值得思考`、`幫助判斷`、`重點不是...而是...` 這類句式只是在形容圖的價值，沒有告訴讀者下一步怎樣看、怎樣分辨或怎樣使用；除非已改寫成來源特定的操作、檢查條件、取捨或判斷標準，否則不得進入鎖定稿。頁碼、1-7 圈號或其他掃描輔助說明也不得冒充全文重點。

## 8. 手繪知識卡片母版

正式圖以乾淨、現代、可教人的 Bauhaus 手繪知識卡片作預設品質方向。若圖像未完全符合這個方向，但核心內容、關係、可讀性、來源註腳與真 PNG 證據都合格，記錄品質提示後可入庫；不可為了風格偏好重生。

Bauhaus 在本規格中是版式語言，不是裝飾風格。它用幾何分區、原色提示、黑白灰基底、清楚對齊和非對稱平衡，幫讀者跟住判斷、流程、差異或限制；不得只在圖面加圓形、三角形或色塊來製造風格感。資訊路徑永遠比風格更重要。

母版目標：

- 固定視覺配方（新生成）：Bauhaus 幾何版式 + 克制的 3D 漸變色光影 + 藝術性手繪筆觸。3D 漸變色只可加強有實際語義的層級、入口、限制或關係，不可遮蓋文字、取代關係表達或變成裝飾背景；手繪必須清楚成熟，不可潦草或童趣化。
- 視覺氣質：像白板筆記、sketchnote、教學講義、手繪整理卡，但有現代幾何秩序與可辨識的層次感。
- 圖像目的：讓讀者更快跟住判斷、流程、差異或限制。
- 視覺邊界：可以有手繪感，但不能潦草、低清、童趣過度或難讀。
- 內容密度：每個主要分區至少承載一個來源對應的可見知識句和一個服務理解的語義圖解；不得把主區留作大面積空白、純裝飾人物或無內容圖示。

基本母版：

- 直幅真 PNG，正式 action 鎖定目標 `1024x1536`、品質方向 `high`，一個 action 只生成一張。
- 實際 PNG 必須符合官方尺寸限制：兩邊均為 16 px 的倍數、最長邊不超過 3840 px、長短邊比例不超過 3:1，總像素介乎 655,360 至 8,294,400。
- 背景使用暖白或白色紙本底，可有極淡灰色 construction grid；正式 PNG 必須是不透明底，不可有 alpha channel 或透明色，不可有粗顆粒、舊紙、報紙、暗角、雜訊或仿古拼貼。
- 色彩以黑、白、灰為基底，點綴明亮紅、黃、藍三原色；綠色只在來源、品牌或語義必要時少量使用，不得成為主色。避免單一色系填滿全圖。
- 標題使用粗筆手寫感，正文使用清楚手寫印刷體。必須像人手整理但仍可讀，不要機械黑體，也不要潦草草書。
- 使用手繪幾何分區、圓角框、底線、箭頭、虛線、圈號、勾選框、便條、旗標或簡單小圖示建立閱讀路徑。矩形、圓形、三角形、粗線、色塊和箭頭都必須對應實際語義，例如決策、分組、警告、入口、出口、比較或限制。
- 頁碼固定右上角，只出現一次。
- 底部只放手寫來源註腳，必要時加一條手繪底線；footer 必須保留本可攜套件的通用簽名 `(創造型 2nd Brain)`，不得漏字、改成其他括號字、加入表情、裝飾尾字或白名單以外的 footer 文字，也不得使用深色全寬 footer 色帶。footer 只可顯示讀者可理解的公開來源標籤；原始發布頁未提供、待核實、來源／作者核對狀態、擷取方式、提交者身分、來源身分、雜湊、審閱或其他任務系統訊息只留在來源稽核、source note、registry 或 receipt，絕不可進入圖面。

使用者提供的評論或整理文字若附有已核實的原文引用，來源註腳須明示「原文參照」，並列出引用資料中已有的原文作者、題名與刊物；作者名只屬於被引用作品，不代表評論／整理文字的作者。引用資料未核實時，不得把該引用放入來源註腳，也不得以提交方式或模糊的「使用者提供文字」代替已核實資料。完整引文若無法在一行清晰呈現，可分成最多兩行；不得為塞入單行而縮小到難以閱讀。

可用版式：

- 條列整理：3 至 5 個重點，每點有手繪圖示或符號、短標題、一句解釋。
- 左右比較：兩個概念、工具、選擇或角色，中央用箭頭、分隔或同源標籤說明關係。
- 流程步驟：1、2、3、4 的行動順序；每步要有產出或停下條件。
- 限制清單：把限制分成「能做 / 不能做 / 先檢查」或其他清楚層級。
- 例子轉譯：抽象原則 + 具體例子 + 一句紅橙色收束。
- 幾何路徑：用 Bauhaus 式幾何區塊和箭頭表達決策、流程、權限、限制門或讀者掃描順序；幾何形狀不可只作裝飾。
- 地圖總覽：只用於來源真的有多個模組、角色或系統關係。

數字標籤按各項分別鎖定；清單的分隔符不是必須畫出的正文。排版可把標籤分開放置，數字及單位仍須逐字讀回，並核對其對應對象沒有互換。編譯提示保留數字欄位的逐項身分，中文或文字寫成的數量同樣鎖定，不能只靠阿拉伯數字辨識或以語義通過欄位略過。

圖示規則：

- 每頁通常以 2 至 5 個手繪圖示或符號已足夠。超出這個範圍本身只是品質提示；只有圖示遮擋核心文字、令關係錯讀或造成明顯閱讀負擔才阻擋。
- 每個圖示必須在 `圖示語義清單` 對應一個可見文字項目及一個語義角色。
- 圖示可用來表示來源類型、角色、流程、限制、提醒或例子；不可只為填空。
- 圖示本身不得含文字、字母、數字、檔名、縮寫、代碼或類似程式碼的符號；正文、標題、數字、年份、金額、百分比、頁碼與底部來源行仍按白名單顯示。

重要收束句：

- 每頁可有一個紅橙色 `讀後收穫` 或 `使用提醒` 區，但只有在它能收束該頁判斷時使用。
- 收束句不得重複正文；它要說出讀者看完後可使用的具體判斷、操作、檢查條件或取捨，不得只說圖有用、重要、實用或有啟發。

## 9. 反例與禁止方向

以下是應記錄並在下次規劃改善的品質提示；它們本身不會阻止正式入庫。只有實際導致核心內容錯誤、關係錯讀、不可讀／裁切、來源註腳或簽名缺失、或內部流程文字外露時，才按本規格的阻擋條件處理：

- 圖面像乾淨 SVG、企業 dashboard、簡報模板、UI card、純裝飾漸層色塊或 vector icon 套件。
- 使用深色全寬 footer 色帶，把來源行做成 app 底欄。
- 完美等寬卡片排版，只有框線沒有手繪閱讀路徑。
- 每格一個 icon，但 icon 不幫助理解。
- 把 Bauhaus 理解成加幾何裝飾，而不是用幾何秩序帶出閱讀路徑。
- 重新回到參考圖的綠色 sketchnote 主視覺，而不是形成獨立母版。
- 用 1、2、3、4 編號製造秩序，但項目之間沒有先後、因果或比較關係。
- 把版本號、容量、方案名稱、欄名反覆放入不同卡片，沒有新語義。
- 大標題佔去過多畫面，正文只剩幾個薄弱框。
- 內容只有名詞列表，沒有背景、用途、後果或下一步。
- 使用生成式泛句作收束，例如只說「有實用性」、「有啟發性」、「真正有用」、「幫助判斷」或「重點不是...而是...」，但沒有來源特定的操作、檢查條件、取捨或判斷標準。
- footer 漏掉 `(創造型 2nd Brain)`、把 `(創造型 2nd Brain)` 改成其他字、或出現額外括號字、表情、裝飾尾字、亂碼、白名單以外文字。
- footer 把「原始發布頁未提供／待核實」、來源或作者核對狀態、擷取／審閱狀態、來源身分或其他任務系統訊息當作對外來源註腳。
- 為了像參考圖而照抄人物、來源、配色比例、句式或版面；參考圖只提供方向，不是模板。

若模型輸出偏 SVG 或 dashboard，下一次規劃的改善優先序是：

1. 先重寫頁面任務與圖面結構，讓它有判斷、流程或對照。
2. 再收緊 prompt 母版，要求 Bauhaus 版式語言、黑白灰基底、明亮紅黃藍提示、手繪 marker、幾何分區、底線、箭頭、紙本底和底部手寫來源行。
3. 把改善寫入下一張尚未派發的圖的鎖定稿。已通過核心驗收的 PNG 不因這些品質提示重生；不得只加「hand-drawn」形容詞就消耗第二次生成。

## 10. Prompt 與生成

正式 prompt 只可由既有 prompt contract 或 Compiler Worker 組裝，不得手寫另一套。模型可見內容只包含固定母版、版面安排和已核定可見文字白名單；來源證據、覆蓋 ID、校對紀錄、欄位名稱、處理狀態、重試原因、路徑與儲存流程不得進入 prompt 的可見文字區。

多頁資訊圖的 prompt contract 必須識別頁碼語境：第 1 頁要使用導讀版面指令，先呈現全文主題、重要性與後續脈絡；後續頁只承接首圖路線並專注本頁任務。`navigation_text` 不得自動進入白名單；可見文字只可使用來源主張、讀者可直接吸收的脈絡句、頁碼、日期與 footer。任何看似 AI 任務要求、製作方法、驗收語、讀回語或閱讀操作語的文字都要在 compile 前停止。

正式生成路線：

1. 完成來源審閱、覆蓋表、每頁鎖定稿與預檢。
2. 編譯正式 prompt、資產路徑與雜湊。
3. 由 Codex imagegen / `gpt-image-2` 生成真 PNG。
4. 保存 action identity、provider/model、prompt hash、PNG SHA-256、尺寸、圖片讀回與語義驗收。
5. `imagegen-complete`、`imagegen-finalize` 或等效完成步驟把通過頁綁回 source slice / Knowledge Package。
6. 既有 ingest / writer 只接收已通過資訊圖驗收的正式 PNG。

正常路徑只有一次 `initial_generation`。沿原始入庫要求的第二次生成只可作 `blocking_repair`，而且必須同時滿足：有實際 PNG 讀回證據、有嚴重內容錯誤或遺漏，以及有明確受影響文字。使用者要求將某來源正式入庫、完成入庫或繼續完成入庫時，即授權該來源每頁的正常首次生成，以及通過上述證據的唯一一次 `blocking_repair`；讀回確認阻斷錯誤後，AI 不再逐頁再次詢問。這項授權不涵蓋第三次生成、沒有阻斷證據的重生、改變來源範圍或其他來源。普通樣式微調、版面偏好、對齊、間距、底部來源行高度、比例或非阻塞幾何差異，不可成為第二次生成理由。一次修復後仍不合格，停止並回到鎖定稿或規格，不開第三輪。

### 已存在的品質型失敗

歷史 PNG 若只因圖示數量、Bauhaus 程度、留白、等寬卡片或一般視覺效益而得到 `reverse_review_failed`，不得重生或重置工作。由 Compiler Worker 對同一 source、page、locked prompt 與 PNG hash 做一次獨立核心重審；新讀回必須證明來源意思、可見文字、關係、可讀性、footer／簽名及內部文字邊界均合格，並保留原失敗、計時與生成次數。

`user_authorized_visual_repair` 只保留給使用者明確要求改圖的情況，從不再因上述品質提示而成為入庫的必要步驟。涉及錯字、否定詞、數字、對象、關係、裁切或來源註腳的核心失敗，仍只可依一輪 `blocking_repair` 規則處理。

提示詞契約升版時，從未派發或產生 runtime 結果的頁面可在同一 job 內升版：必須封存舊 action／prompt／ledger 快照、拒絕舊 action 重播，並以新 hash 重新授權。已存在 PNG 的頁面不可藉此升版或重生；它只可保留原 prompt 和 bytes，並以本節的現行核心重審作 writer admission 的唯一橋接證據。

### 已完成圖片的明確文字修訂

使用者明確要求修正已完成圖面文字時，沿 `prepare-infographic-revision` 的 `mode=same_job_text_revision` 處理：保留原 `job_id`、來源身分、首次接受時間、頁面 ID 及歷史完成回條。修訂稿必須先通過第 7 節的獨立冷讀及來源忠實核對；再以原已接受 PNG 作風格參照，修改文字，不另開首次生成工作。

修訂計劃使用 `infographic_revision_plan_v1`，包含原 `job_id/source_id/source_identity`、唯一 `revision_id`、保留證據覆蓋的 `coverage_units`、全部 `infographics`，以及 `authorization`（`authority=current_user_message`、使用者原指令 `user_instruction`、`additional_attempts_per_page=1`）。只可修訂圖面文字及其主來源逐字引文，不換來源、分析正文或頁面身分。計劃路徑由原工作保存。

```text
python -B tools/compiler_worker_v2.py --root "." prepare-infographic-revision --kp-file "<目前完成包>/knowledge_package.json" --plan-file "<原工作內的文字修訂計劃>.json"
python -B tools/brain.py rail advance --job-id <原工作ID>
```

同一工作以版本子目錄承接新稿，原回條、原圖與歷史 ledger 不覆寫。新嘗試種類為 `user_authorized_text_revision`；累計次數從不可變歷史逐次推導，不以新版本重設。每頁只派發此次明確授權的一次修圖；失敗保存原次數，不自動開下一輪。準備或授權中斷只能恢復同一交易及 action identity；pending action 先核對實際工具結果，不再派發。

若使用者在實圖文字缺漏反審後另行明確授權一次局部補字，沿同一 `imagegen-authorize --reason user_authorized_text_revision --authorization-file` 處理。授權使用 `infographic_text_correction_authorization_v1`，綁定工作、來源、頁面、失敗 action／PNG、完整 prior attempts hash、逐字 `restore_text`、使用者原話及 `additional_attempts=1`；以該失敗圖作參照，只補已觀察且在原鎖稿內的文字。不得由原入庫授權推定額外次數；不新增工作、不改鎖稿、不覆寫失敗紀錄。

必須把 action 的完整 `imagegen_tool_arguments` 原樣傳入 Codex 內建修圖工具，並保存實際派發參數。新 PNG 除正常反審外，須以 `text_revision_review` 記錄 `accepted_style_preserved`、`new_text_complete` 及具體 `evidence`。writer 重驗來源版本、參照圖、鎖稿與實際派發，不接受只填相同 hash 的自述。新圖全部通過後才更新正式指向；失敗時既有正式成果仍可讀。

## 11. 圖片讀回與入庫驗收

每張正式 PNG 入庫前必須通過下列檢查：

1. 真 PNG 及 provider/model 證據成立，並綁定 `codex_imagegen / gpt-image-2`。
2. PNG SHA-256、prompt hash、資產路徑、attempt ledger 與鎖定稿一致。
3. 圖內可見文字與鎖定稿一致，並已按第 7 節通過 `自足、短而厚實` 檢查；沒有未授權額外文字、欄位名、處理狀態或後台內容。
4. 頁碼只在右上角；底部來源行完整、可追查、未裁切。
5. 每頁回答自己的讀者問題，並能說出一句讀後收穫。
6. 多頁分工互補，沒有語義重複、硬砌頁數或同一數字無意義反覆。
7. 記錄圖型與 `visual_structure` 是否提供更清楚的閱讀路徑；純文字框或關係表達較弱本身只作質量提示，除非令來源關係錯讀或核心文字不可讀。
8. 手機縮圖下主題、段標與主要正文仍可讀。
9. 沒有裁切、遮擋、缺字、錯誤關係、明顯亂排或資訊層級倒置。
10. 記錄是否達到手繪知識卡片品質方向，以及是否有下次可改善的閱讀路徑；這一項單獨不阻擋。
11. Source note、vault asset、成果頁與 manifest 讀到同一批正式 PNG 路徑及雜湊。

自動視覺 QC 只處理尺寸、可讀性、底部來源行、裁切與安全區等可機器化項目；它不能代替獨立讀回。若獨立讀回指出來源意思、關係、可讀性、footer／簽名或內部文字有具體問題，仍然不合格。

## 12. 第三方讀者評核

正式入庫前，除機器 gate 外，必須以獨立讀者角度作一次短評。短評用來找出核心理解風險與下次品質改善，不是以個人美術偏好反覆退件：

- 這張圖對第一次讀者有甚麼幫助？
- 讀者看完能否更快理解來源，而不是只看到零散摘要？
- 哪些文字、數字、圖示或分區沒有實際用途？
- 是否有更合適的視覺模型，例如流程、對照、層級、場景、檢查表、證據階梯？
- 是否存在「工具通過但用戶不會覺得有用」的假合格？
- 圖面是否有手繪知識卡片感，而不是 SVG 偽圖？（品質提示）

短評如指出具體缺漏，令讀者無法辨認對象、必要術語、動作條件／結果，或無法回答本頁問題，即為內容理解失敗，須在鎖稿前修正；不得以「只是硬砌／仍需回原文」降為提示。既有來源意思、數字／否定／對象、關係、可讀性、footer／簽名及內部文字阻擋保持不變。純美術偏好、圖示數量、留白或一般視覺效益仍只作提示。新 PNG 反審須保存 `reader_comprehension` 的實際圖面回答、關係解釋及三類缺口清單；不得只比較白名單。歷史完成 receipt 不追寫通過；遇到使用者要求修正，以明確授權的原工作修訂處理，不自動增加生圖次數。

## 13. 常見失敗與防錯

過度框架化：舊規格容易把每篇內容塞入固定三頁、固定卡片、固定深藍 footer。v3 以讀者問題決定頁數與圖型；沒有不同理解任務就不要多頁。

SVG 偽圖：線條太完美、圖示像 icon library、卡片像 UI 元件、底部像 app footer。修正方式是改用手繪 marker 線、手繪框、底線、箭頭、圈號、紙本底與手寫來源行。

文字太薄：圖內正文未通過第 7 節 `自足、短而厚實` 檢查，只寫名詞、標籤、版本號或限制詞，沒有交代場景與後果。修正方式是先寫 `本頁讀者問題` 與 `本頁一句讀後收穫`，再重寫正文短句。

比較失敗：左右欄、矩陣或編號清單沒有共同比較基準。修正方式是在 `visual_structure.rows[].basis` 逐列寫清比較基準。

流程失敗：箭頭只是裝飾，讀者看不出下一步由甚麼條件觸發。修正方式是改用 `decision_path` 或在步驟中加入產出與停下條件。

限制清單失敗：把所有限制放同一層，讀者不知道哪項影響使用、哪項只是環境要求。修正方式是分成「使用前判斷」、「發布限制」、「可用性門檻」等語義層。

圖示失敗：圖示不表達新資訊。修正方式是刪圖示，用位置、分區、線條、色彩或短標籤表達關係。

重複失敗：同一版本號、容量、方案名或日期反覆出現。修正方式是保留一次，其他位置改寫為關係或後果；若沒有後果就刪除。

入庫後品質提示：機器欄位齊、PNG 可讀、底部來源行正確，但第三方讀者認為仍可更有用。修正方式是按第 12 節記錄下一次未派發頁面的規劃改善；純品質偏好不構成重生理由；有具體理解缺漏則依第 7、12 節處理，生成次數與修訂授權仍依第 10 節。

## 14. 可攜使用與證據邊界

本套件保留完整 Bauhaus 手繪知識卡片規格與生成閘門；通用簽名是 `(創造型 2nd Brain)`，不帶原專案擁有者身份。只有規格、唯一 prompt renderer 及其讀回一致時才可使用。不得把本文件中列出的內容形態解讀為新增原生入庫種類；正式輸入仍依 [來源與 writer 規格](URL到輸出模板規格.md)。

新電腦使用前要確認當前 Codex runtime 確有內建圖像生成和圖片讀回能力。只可使用內建功能，不得改用 OpenAI API key、SDK 或自製圖片 worker。缺少能力時保存原工作與鎖定計劃，報明確阻塞；不能用 fixture 或舊圖冒充本次正式生成。

離線驗收可證明 parser、契約、路徑、內容映射、恢復及假 receipt 拒絕；不能證明 live 生成品質、服務速度或新電腦登入狀態。歷史成果與私人樣本不隨套件附送，也不充當新圖模板。
